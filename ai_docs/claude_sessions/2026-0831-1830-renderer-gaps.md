## Goal

Close all four of the ROADMAP's renderer gaps in one pass:

- Proportional flex weights on iOS (noted as "needs a custom SwiftUI `Layout`")
- `AlignItems: "stretch"` on both native renderers
- A `ContentMode` prop on `Image`
- A native disabled state — "no renderer carries one"

They looked like four unrelated items and turned out to share one shape: each
is a place where the Go DSL *declares* something CSS-shaped that a platform
toolkit has no direct word for, and the previous answer was either an
approximation or nothing at all.

## 1. Proportional flex weights — a SwiftUI `Layout`

Compose has `Modifier.weight`, which is proportional by construction, so
Android had always been right. SwiftUI has no weight, and the renderer gave
every grower a `.frame(maxWidth: .infinity)` — which makes a stack split
leftover space **equally**. So one Go declaration rendered 75/25 on Android and
50/50 on iOS.

`GrMobFlexLayout` (a `Layout`) now replaces `HStack`/`VStack` for `Row` and
`Column`, running the CSS algorithm directly:

```
base_i    = subview ideal size along the axis     (flex-basis: auto)
natural   = sum(base_i) + spacing * (n - 1)
free      = container - natural
free > 0  -> size_i = base_i + free * weight_i / sum(weight)   [grow]
free < 0  -> size_i = base_i + free * base_i   / sum(base)     [shrink, flex-shrink:1]
leftover  -> justify-content, as offsets rather than sizes
```

Two things came along with it, neither of them the task:

- **`justify-content` is exact.** The Spacer emulation could not tell
  `space-around` from `space-evenly` — CSS gives space-around *half-width*
  edge gaps — and rendered both as evenly. It also put views in the tree that
  the app never declared.
- **`crossAlignmentV` died with the HStack it served.** Removed; the compiler
  is the proof nothing referenced it. `crossAlignmentH` survives for
  `GrMobList`, which cannot become a custom Layout without giving up laziness.

### Two decisions inside it

**Hug vs. fill.** A CSS flex container is a block box and fills its line; a
SwiftUI stack hugs. The layout claims the offered main extent only when
something would *use* it — a grower, or a justify-content that positions
against the far edge — and otherwise reports its natural size. That is not the
CSS rule; it is what reproduces every layout written before this file existed.
An infinite proposal is treated as unspecified: it is SwiftUI probing for a
maximum, not an offer to fill the universe.

**Weight travels as a `LayoutValueKey`, not a stored array.** A `Layout`
receives children as opaque proxies — `subviews[i]` cannot be traced back to
the `GrMobNode` it came from — so a parallel array would silently mis-align
the moment SwiftUI flattened a Group or dropped an empty view.

### The arithmetic was extracted so it could be tested

`ios/GrMob/Runtime/GrMobFlex.swift` holds `GrMobFlexSolver`: pure, `import
CoreGraphics` and nothing else. A `Layout` can only be exercised by mounting
it in a view hierarchy (simulator); everything actually easy to get wrong here
is a function from numbers to numbers.

`ios/verify/flex.swift` checks it against values **derived from the CSS spec,
not from the implementation** — so a failure means the renderer disagrees with
Compose and the browser, not merely that the code changed.

## 2. `AlignItems: "stretch"`

A stretched child is *sized* to the cross axis, not *placed* along it, which is
why neither toolkit's alignment enum has the value: both are start/center/end.

- **iOS** — the layout proposes the full cross extent to each child.
- **Android** — Compose cannot express it at the container, so the children
  carry `fillMaxWidth()` (Column) / `fillMaxHeight()` (Row). Same shape as
  weight: a cross-axis decision only the parent knows, applied to the child.
  A stretched Row is additionally pinned to `IntrinsicSize.Max`, or a bare
  `fillMaxHeight` would resolve against the *parent's* maximum (usually the
  screen) instead of the tallest sibling.

Two Android combinations documented as unsupported, both fixed by giving the
Row an explicit `Height`: a `List` inside a stretched Row (a lazy list throws
rather than answer an intrinsic-height query), and a stretched Row that is
itself a `FlexGrow` child of a Column (the intrinsic height overrides the
weight-derived one; the conflict is undetectable there because `extra` is
opaque and the same FlexGrow under a *Row* parent sets width, where the
intrinsic height is still right).

**A third target turned out to be broken too.** The WASM runtime's
`styleFromGrMob` mapped fourteen properties and none of the flex group, so
`AlignItems` — stretch included — was declared in Go and silently dropped on
the web while both natives honored it. A plain `<div>` is block flow and
ignores `gap`, `justify-content` and `align-items` entirely, so the container
has to be made flex first. Now emitted, mirroring `htmlout`'s rule.

`Display` is deliberately still **not** emitted there: Go's `DisplayMode`
carries values that are not CSS display keywords ("visible", "hidden"), and
unlike `htmlout` — where an invalid declaration is dropped and the earlier
`display:flex` survives — assigning one through `el.style` would overwrite the
flex display in the object first and *then* be rejected, leaving the container
in block flow.

## 3. `ContentMode` on `Image`

`core.ImageWithMode(src, mode, styleProps...)` — a separate builder rather than
a variadic change, following the `InputWithSubmit` precedent: every existing
call site keeps compiling, and the mode is a visible required argument at the
sites that care.

| `core.ContentMode` | SwiftUI | Compose | CSS |
|---|---|---|---|
| `Fit` (default) | `scaledToFit()` | `ContentScale.Fit` | `object-fit: contain` |
| `Fill` | `scaledToFill().clipped()` | `ContentScale.Crop` | `object-fit: cover` |
| `Stretch` | `resizable()` | `ContentScale.FillBounds` | `object-fit: fill` |
| `Center` | intrinsic size, clipped | `ContentScale.None` | `object-fit: none` |

An empty mode is **omitted from Props entirely** rather than written as "fit".
Each renderer defaults to fit on a missing prop, and leaving it out keeps the
prop map — and therefore the reconciler's `update-props` diffs and every
existing snapshot — byte identical to what `Image` produced before the feature.

`Fill` and `Center` crop on every target. The first draft of the doc comment
said Fill "only crops when the box is clipped"; that was true of the SwiftUI
path as first written and wrong for the other two, so the renderer got an
explicit `.clipped()` and the doc got corrected rather than the caveat kept.

## 4. Native disabled state

`Style.Disabled` + `core.Disabled(bool)`. **On Style, not Props** — the same
argument the accessibility fields carry: every builder already takes
StyleProps, so Button, the inputs, the checkbox and any tappable container get
it without a signature change, and it patches like any visual property.

| target | mapping |
|---|---|
| Android | `enabled = false` on the material3 control; the gesture modifier is *dropped* from a tappable box (which also drops the ripple and the a11y actions) |
| iOS | `.disabled(true)`; `GrMobGestures` refuses to attach |
| HTML / WASM | the `disabled` attribute on form controls; `aria-disabled` + `pointer-events:none` elsewhere |

Three points that shaped the code:

**The handler stays registered.** `core.Button` registers whatever it is given
and a nil `func()` in the registry panics when a native tap races the patch
that disabled the control. Disabling is the *renderer's* job; dropping the
callback is not a substitute, and the callback ID is still in the exported
markup (there is a test for that).

**It propagates.** SwiftUI's `.disabled` and CSS `pointer-events:none` both
reach the subtree; Compose has no equivalent. Rather than ship "the node only"
on one platform and "the node and everything under it" on two, Android gained
`LocalGrMobDisabled`, opened once in `RenderNode` (which split into
`RenderNode` + `RenderNodeContent` for it). That is what makes "freeze this
section while the form submits" a single declaration.

**material3 would have overruled the theme.** With `enabled = false` it paints
its own disabled tones over whatever colors were passed, so
`disabledContainerColor` / `disabledContentColor` are fed the same values —
Go stays the single source of truth for the palette.

`Disabled` takes a bool rather than being a no-arg flag like
`AccessibilityHidden()`: `UseStyle`'s "a zero value means unset" rule leaves
`Disabled(false)` as the only way to force a node back to enabled.

### `components.Button` lost its emulation

The widget appended `", disabled"` to the accessibility label — the
`", selected"` convention Chip and ListRow use — *because* no renderer carried
the state. Now that all three do and announce it themselves (VoiceOver
"dimmed", TalkBack's Disabled property, the HTML attribute), keeping the suffix
would announce it twice. Removed, along with the `accessibilityLabel()` helper;
`TestButtonDisabled` was rewritten to assert `Style.Disabled` and a clean label.
The prop is appended *after* the caller's `Style`, so a one-off override cannot
re-enable the control, and there is a test for that too.

## Testing

**Go — new:** `core/image_test.go` (mode present/absent/round-tripped, Disabled
on four different builders, the handler surviving, `Disabled(false)` clearing
what `UseStyle` cannot), plus ~130 lines in `htmlout/export_test.go`

rather than emitted as an invalid declaration, the declaration joining the
*existing* style attribute — an element carries exactly one — the disabled
attribute on all six control types, `aria-disabled` + `pointer-events` on a
container, and `stretch` making a container flex).

`TestUseStyleMergesEveryField` caught `Disabled` needing an `applyTo` branch on
its own, which is what that reflective walk exists for.

**Swift — new:** `ios/verify/flex.swift`, wired into the existing harness, and
`run.sh` now also **typechecks the whole view layer** (`swiftc -typecheck
../GrMob/Runtime/*.swift`). That is new coverage for `Renderer.swift`, which
had none: it carries a hand-written Layout and a deep opaque-type modifier
chain, both of which fail at compile time in ways no data-layer test notices.

### Mutation-checked

Twelve deliberate breaks, each confirmed to fail before the test was kept:

| break | caught by |
|---|---|
| drop `Disabled` from `applyTo` | `TestUseStyleMergesEveryField` + the clear test |
| always emit `contentMode` | `TestImageOmitsContentModeByDefault` |
| drop the htmlout disabled attribute | all six control subtests |
| let a caller `Style` re-enable a Button | both `TestButtonDisabled` subtests |
| equal split instead of proportional | 4 flex assertions (**the original bug**) |
| growth replaces the base instead of adding | 4 flex assertions |
| `space-around` approximated as `space-evenly` | 2 flex assertions (**the old emulation**) |
| always fill, never hug | `hug: no grower, no justify` |
| drop the negative-size clamp | *initially missed* — see below |

The clamp mutation exposed a weak test. `main: 0, bases: [100,100]` cannot
drive the shrink formula below zero: each child gives up its own share of a
deficit that is at most the content itself. The **spacing** is what makes it
reachable — gaps are not shrinkable — so the case became `spacing: 20`, which
lands at `-10` unclamped. Re-run: caught.

All backups diffed clean against the originals afterwards.
